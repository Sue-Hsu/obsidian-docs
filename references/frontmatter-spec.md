# Obsidian Frontmatter 規格指南 (Frontmatter Spec)

本文件定義所有寫入 Obsidian 筆記時，必須包含的標準 YAML Frontmatter 格式、資訊資產密等分類、發布協議屬性與維護準則。

---

## 1. 核心欄位規範

所有受管理的 Markdown 筆記，最上方必須包含標準 YAML Frontmatter：

```yaml
---
類型: "<筆記類型>"
專案: "<專案名稱>"
建立日期: YYYY-MM-DD
修改日期: YYYY-MM-DD
狀態: "<當前狀態>"
密等: "內部使用"
標籤:
  - "<主要標籤>"
  - "專案/<專案名稱>"
---
```

### 核心欄位詳細說明

| 欄位名稱 | 必填 | 格式 / 允許值範例 | 說明與維護規則 |
|---|---|---|---|
| `類型` | 是 | `需求訪談`、`產品規格`、`變更紀錄`、`研究筆記`、`跨專案決策`、`協作任務`、`通用文件`、`AI 提案`、`專案地圖`、`資安審查`、`外部評估` | 標明筆記的本質角色。 |
| `專案` | 條件 | 例如：`ecommerce-web`、`data-scraper`（外部評估筆記可標記為 `外部資源` 或省略） | 該筆記所屬的專案純名稱（年月前綴 `YYYY-MM_` 僅用於實體資料夾名稱）。 |
| `建立日期` | 是 | `YYYY-MM-DD`（ISO 8601） | 筆記首次建立當日的真實日期。建立後永久保留原值以維持建立脈絡。 |
| `修改日期` | 是 | `YYYY-MM-DD`（ISO 8601） | 每次被 AI 或使用者編輯時，更新為當天真實日期。 |
| `狀態` | 是 | 依文檔本質分流維護（見下方狀態列舉規範） | 分別獨立維護文件狀態與任務狀態；狀態跳轉須具備真實驗證或決策依據。 |
| `密等` | 選填/預設 | `公開`、`內部使用`、`機密`（未特別標註者預設為 `內部使用`） | 依循 ISO 27001 資訊資產分類原則。脫敏資安摘要預設為「內部使用」；若包含可利用弱點 PoC、帳戶資訊、內部拓撲或敏感路徑則標為「機密」；凡準備對外發布之文件，須另行於發布目錄完成去識別化與發布審查並標為「公開」。 |
| `標籤` | 是 | YAML 清單，至少含類型與 `專案/<專案名稱>` 或 `主題/<大主題領域>` | 供 Obsidian 標籤檢索與知識圖譜過濾使用。 |

### 狀態 (Status) 列舉與治理規範

1. **一般文件狀態 (Document Status)**：
   - `草稿`：新建立、撰寫中或尚未具備實質驗證之文檔（預設狀態）。
   - `提案中`：已完稿待架構師/PM/使用者審核評估。
   - `已驗證`：經過實質測試、命令執行、驗收測試通過並檢附客觀證據者。
   - `使用中`：正式生效啟用，作為現行單一事實來源 (SSOT) 之基準文件。
   - `已取代`：已有新版本規格或契約替代，內文頂部須標註替代新文檔連結。
   - `已廢棄`：依 ISO 廢棄流程停用，不可直接刪除檔案，內文須保留廢棄原因與歷史脈絡。

2. **協作任務狀態 (Task Status)**：
   - `待辦`：尚未排程指派。
   - `規劃中`：正在梳理範圍與 AC。
   - `進行中`：目前負責的 Agent 正在執行工作。
   - `待審閱`：已附上執行與驗證證據，等待主導 Agent 或使用者判斷尚未核可的條件。
   - `受阻`：遭遇技術瓶頸或外部阻礙，已記錄 Blocker 與替代選項。
   - `完成`：客觀驗收條件已有執行與檢查證據，且需由使用者判斷的條件已獲核可。直接工作時可由當前 Agent 核對客觀證據後結案；派工時由主導 Agent 審查 Worker 交接後結案。

3. **發布狀態 (Release Status - 依需求選用)**：
   - `內部專用`：絕不對外公開之內部設計或專案資產（預設）。
   - `未發布`：規劃對外交付，但尚在內部編修階段。
   - `待發布`：已通過發布安全檢核閘門（去識別化與死鏈隔離），等待上線交付。
   - `已發布`：已正式釋出予客戶、開源社群或外部使用者。

4. **檢測驗證狀態 (Verification Status - 資安審查專用)**：
   - `未受測 (NOT_TESTED)`：尚未執行檢測之規劃項目或因缺乏環境尚未排程實測者。
   - `通過 (PASS)`：由符合驗收標準之客觀實測指令與日誌輸出支持且 0 發現者；工具零發現時記錄其覆蓋範圍與限制。
   - `發現弱點 (FAIL)`：檢測出待處置之安全風險或弱點。
   - `不適用 (NOT_APPLICABLE)`：因架構調整或專案性質不適用該項檢測。

5. **漏洞修復狀態 (Remediation Status - 資安審查專用)**：
   - `待修復`：弱點已確認，等待立項或開發修復。
   - `修復中`：已指派工單，正在進行防護代碼修訂。
   - `已修復`：已完成修復並通過複測驗證。
   - `誤報 (False Positive)`：經架構核對確認非實際弱點。
   - `接受風險`：評估後判定業務合理或受控環境下可接受之殘餘風險。
   - `不適用 (規劃階段)`：資安基準規劃階段，尚未執行實體檢測。

6. **資安放行建議與實際發布授權（職責分離 - 資安專用）**：
   - **資安放行建議 (Security Gate Recommendation)**：
     - `建議放行`：檢測全數通過或殘餘風險受控，達到技術安全門檻。
     - `條件式放行`：存在中低風險待修復或特定環境限制，附帶條件允許過渡。
     - `不建議放行`：存在重大未修復弱點或關鍵維度未測，未達安全門檻。
     - `未評估`：尚未執行基準評估或處於規劃初稿。
     > [!IMPORTANT]
     > 資安檢測通過僅代表技術面達到安全防護門檻，絕不代表已取得 commit、部署、公開發布、DNS 或雲端設定變更授權。
   - **實際發布授權 (Release Authorization)**：
     - `已授權`：經產品主管、架構師或發布審批委員會 (CAB) 正式核可部署或發布。
     - `未授權`：尚未獲得正式變更管理審批（預設）。
     - `條件式授權`：獲得限定灰度、受控預覽或限定 IP 白名單之變更授權。
     - `不適用`：純內部規劃、非發布性資產或單純研究報告。

7. **弱點清單三軸狀態 (Findings Register Tri-State)**：
   在個別檢測報告與總覽之 Findings 表格中，必須分開獨立記錄：
   - `弱點確認狀態`：`待確認`、`已確認`、`誤報`
   - `修復狀態`：`待修復`、`修復中`、`已修復`、`接受風險`、`不適用`
   - `複測狀態`：`未複測`、`通過`、`未通過`、`不適用`

## 2. 擴充欄位規範（依文檔類型選用）

特定類型的筆記可補充專用中文字段：

### 2.1 對外發布與交付文檔（`50 專案文件/05 對外發布/`）
- `發布狀態`: `未發布`、`待發布`、`已發布`、`內部專用`
- `發布版本`: 例如 `v1.0.0`、`v2.1.0`
- `發布日期`: `YYYY-MM-DD`
- `目標對象`: 例如 `外部開發者`、`終端使用者`、`客戶稽核團隊`

### 2.2 規格、技術契約與架構文件（`50 專案文件/`）
- `對應版本`: 實際適用的 commit、tag 或版本（如 `v1.0.0`、`commit:a1b2c3d`；尚未驗證時可留空並保持 `狀態: 草稿`）
- `關聯PR`: 相關 PR 或審閱連結（例如 `#42` 或 PR URL）
- `廢棄替代`: 當狀態為 `已取代` 或 `已廢棄` 時，填入替代文檔之 Wiki-link（例如 `[[50 專案文件/01 規格與契約/SPEC-002-新規格|SPEC-002]]`）

### 2.3 專案地圖（`10 專案地圖/`）
- `儲存庫`: 例如 `'C:\Projects\my-project'` 或 `'/workspace/my-project'`（Windows 路徑建議使用單引號包覆，確保 YAML 穩定解析）。
- *附註*：專案地圖之 Properties 下方第一行，必須強制維護 `> [!FOCUS]` 現況焦點指針區塊。

### 2.4 協作任務（`60 協作任務/`）
- `任務編號`: 例如 `DEV-001`、`COLLAB-001`、`FIX-001`（全生命週期自然遞增，跨版本不重置）
- `負責AI`: 例如 `Antigravity`、`Codex`
- `狀態維護者`: 目前唯一可更新該任務卡狀態的 AI 或人；直接工作時由當前 Agent 維護，派工時依交接轉由主導 Agent 維護。

### 2.5 資安審查（`70 資安審查/`，包含具體檢測報告與 `SEC-000` 總覽）
資安筆記統一遵循以下標準 Frontmatter 欄位名稱與列舉值（基準報告與增量報告共用）：
- `報告編號`: 例如 `SEC-001`、`SEC-002`（全週期流水號連續記錄）
- `風險等級`: `嚴重 (Critical)`、`高危 (High)`、`中危 (Medium)`、`低危 (Low)`、`資訊 (Info)`、`待評估 (Pending)`
- `評估編號`: 例如 `ASM-20261022-01`（適用時填寫，對應 assessment_id）
- `評估模式`: `基準規劃`、`靜態分析 (SAST)`、`動態檢測 (DAST)`、`依賴分析 (SCA)`、`秘密掃描 (Secrets)`、`架構審查`、`滲透測試`、`手動稽核`、`增量評估`、`綜合評估`
- `來源版本`: 測試針對的代碼基準，例如 `main @ commit:a1b2c3d`、`v1.0.0-rc1`、`PR #42`，非 Git 專案可使用檔案雜湊或版本識別碼
- `基準評估編號`: 增量評估時填寫關聯之基準 assessment_id，例如 `ASM-20261020-01`（初次基準報告可留空或填寫自身編號）
- `基準來源版本`: 增量評估時填寫依據之基準代碼版本，例如 `main @ commit:a1b2c3d`
- `驗證狀態`: `通過 (PASS)`、`發現弱點 (FAIL)`、`未受測 (NOT_TESTED)`、`結果未定 (INCONCLUSIVE)`、`不適用 (NOT_APPLICABLE)`（資安規劃書標記為未受測；PASS 必須由實測證據支持；工具零發現時記錄覆蓋限制；檢測受阻或需進一步釐清時標記為 INCONCLUSIVE；未受測範圍維持 NOT_TESTED）
- `檢測工具`: 例如 `Semgrep OSS v1.90.0`、`Gitleaks v8.18.0`、`OWASP ZAP v2.14.0`、`手動架構稽核`（含工具與規則庫版本）
- `修復狀態`: `待修復`、`修復中`、`已修復`、`誤報 (False Positive)`、`接受風險`、`不適用 (規劃階段)`（Frontmatter 屬性採標準全稱；內文表格 Findings 欄位為排版簡潔允許精簡為待修復/修復中/已修復/誤報/接受風險/不適用）
- `資安放行建議`: `建議放行`、`條件式放行`、`不建議放行`、`未評估`（僅代表技術面是否達到安全門檻）
- `實際發布授權`: `已授權`、`未授權`、`條件式授權`、`不適用`（代表管理面是否正式取得 commit、部署、公開發布、DNS 或雲端設定變更授權；兩者嚴格分離，落實職責分離原則）

- **密等分類與資訊資產防護（ISO 27001）**：
  - 脫敏資安摘要預設標記為 `內部使用`。
  - 凡筆記內容包含具體可利用弱點 PoC、帳戶資訊、內部拓撲或敏感系統路徑時，密等必須強制標定為 `機密`。
  - 對外版本（如提供第三方客戶或稽核團隊之報告）必須另行於 `50 專案文件/05 對外發布/` 產出，嚴格完成去識別化脫敏與發布審查後始得標為 `公開`。
- **原始掃描報告受控存放與銷毀標準**：
  - 儲存位置優先級：原始掃描報告（如工具 Raw JSON/XML、DAST 請求封包、Burp/ZAP Session）優先保存在 Git repo 與 Obsidian Vault 之外的獨立受控安全儲存體中。
  - Repo 內存放限制：若因自動化管線必須暫存於 repo 內，必須確認已加入 `.gitignore` 徹底排除於 Git 版控、CI/CD 建置產物（Artifacts）及正式部署內容中，且必須執行前置脫敏淨化，移除所有 Cookie、token、Session、私人郵件、帳戶識別資訊（PII）以及完整原始 HTTP 請求/回應封包。
  - Vault 留存邊界：Vault 內嚴禁存放原始日誌大檔，只保留去識別化摘要、檔案完整性雜湊（如 SHA-256）、保存期限與受控位置說明。
  - 安全清理與銷毀：期滿清理時，依儲存媒體與平台採用可驗證的永久刪除、加密金鑰銷毀或組織核准的資料清理程序，嚴禁無依據之隨意刪除。

### 2.6 外部評估（`※_外部評估/`）
- `評估主題`: 例如 `PromptGenius`、`premlogin`、`sqlmap`
- `來源網址`: 原始 GitHub 倉庫、Chrome 商店或官網 URL
- `來源類型`: `GitHub`、`Chrome插件`、`網站`、`本地軟體`、`API服務`
- `評估目的`: `資安審查`、`功能了解`、`訂閱評估`、`技術選型`、`綜合評估`
- `評估AI`: 例如 `Antigravity`、`Codex`
- `風險等級`: `嚴重 (Critical)`、`高危 (High)`、`中危 (Medium)`、`低危 (Low)`、`安全/無顯著風險 (Safe)`、`不適用 (N/A)`

### 2.7 需求訪談、研究、提案與決策
- 需求訪談：`訪談編號`（例如 `INTV-001`）
- 跨專案決策：`決策日期` (`YYYY-MM-DD`)、`決策者`（例如 `人類架構師`）
- 研究筆記：`來源`（原始參考連結或文獻來源清單）
- AI 提案：`來源任務`（關聯的協作任務編號或討論脈絡）

## 3. 維護準則

1. **增量更新保留歷史**：更新既有檔案內容時，先讀取原有 frontmatter，保留 `建立日期` 與自訂欄位；只更動有證據支持的 `狀態` 與 `修改日期`。任務卡更新前核對目前 `狀態維護者`，避免兩個 agent 同時寫入衝突。
2. **範本變數精準置換**：寫入前將範本中的 `{{date:YYYY-MM-DD}}` 或 `<專案名稱>` 等佔位符，全部替換為真實日期與專案命名。
3. **無 BOM UTF-8**：所有檔案格式一律採用 UTF-8 without BOM，換行符號為 LF (`\n`)。
4. **資訊資產防護（ISO 27001）**：凡密等標示為 `公開` 或存放於發布目錄者，發布前確保所有帳密、內部 IP 與本機實體路徑均已完成去識別化脫敏處理。
5. **完全自包含 (Self-Contained)**：所有欄位定義與規格已完整具備，需要對照完整範例時請直接參閱 [references/examples.md](examples.md)。
